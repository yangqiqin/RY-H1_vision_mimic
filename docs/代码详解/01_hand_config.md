# `hand_config.py` 代码详解 —— RY-H1(16) 灵巧手配置单点（Windows 版）

> **文件**：`rycan_hand_windows/hand/hand_config.py`（共 67 行）
> **角色**：整个"睿研 RY-H1(16) 灵巧手视觉动作模仿系统"（Windows 版）的**配置单点**——所有与灵巧手硬件相关的数值常量、协议指令码、换算系数全部集中在此，被换算层（`angles2motor.py`）与控制层（`hand_controller.py`）引用，再经 `hand/__init__.py` 汇总导出给 GUI 与各 App。
> **设计依据**：《RY-H1(16)灵巧手用户使用手册》+ 官方 demo（知识库中收录的 `RyHandLibCANII_rs485_pcan_16.py` 等，尤其 demo 的 `update_motor_positions` 换算函数）。
> **配套阅读**：`docs/代码详解/02_angles2motor.md`（换算层）、`03_hand_controller.md`（控制层）——本文只讲配置本身。

## 1. 文件在系统中的位置与数据流

### 1.1 系统全链路数据流

```
摄像头(RealSense/L515)
   │  深度+RGB 帧
   ▼
vision/hand_pose.py      MediaPipe 手部姿态 → 21 关键点 → 16 关节角度（弧度）
   │
   ▼
vision/postprocess.py    精度后处理（平滑/滤波/时序一致性）
   │  16 关节角度（弧度，顺序 = 关节 ID 1~16）
   ▼
hand/angles2motor.py     角度 → 电机指令换算（读取本文件的 K12/K3/K16、ANGLE_RANGE_DEG…）
   │  16 个电机位置指令（0~4095）
   ▼
hand/hand_controller.py  ctypes 调用厂家 RyCAN SDK（RyhandLibx64.dll）
   │  RyMotion_ServoMove_Mix / _Speed（0xAA / 0xA1 指令）
   ▼
hand/transport.py        PCAN / CANalyst-II / RS485 物理帧收发
   │  CAN 帧 / RS485 0xA5 封包
   ▼
RY-H1(16) 灵巧手          16 个电机执行动作
```

### 1.2 本文件在链路中的位置：**配置单点**

`hand_config.py` 不参与任何运行逻辑——它**只声明常量**。所有下游模块直接 import 这些常量，而不是各自硬编码"魔法数字"：

```
                    ┌─────────────────────────────┐
                    │   hand_config.py (本文件)     │
                    │   常量 / 字典 / 换算系数 / 指令码 │
                    └──────────────┬──────────────┘
                                   │ import
        ┌──────────────────────────┼──────────────────────────┐
        ▼                          ▼                          ▼
 hand/angles2motor.py       hand/hand_controller.py     hand/__init__.py
 (换算层)                    (控制层)                     (包级再导出)
        │                          │                          │
        ▼                          ▼                          ▼
   （被 hand_controller 调用）  gui/main_gui.py          gui/hand_gui.py
                                gui/hand_gui.py          apps/mimic_demo.py
                                apps/diag_motor.py       apps/test_hand.py 等
```

**为什么单独抽成一个文件（配置单点原则）**：
1. **一处修改、全局生效**：例如把第 16 关节行程上限从 110° 改成别的值，只需改 `ANGLE_RANGE_DEG["joint16"]` 与 `K16`，换算层与控制层自动跟随；
2. **消除魔法数字**：换算层里出现的是 `K12` 而不是 `45.5`，读代码的人能立刻知道它"来自配置"；
3. **与手册/demo 对齐的可审计性**：所有"为什么是 90/75/110/4095"的答案都集中在一个文件里，方便对照《RY-H1(16)灵巧手用户使用手册》审查。

> ⚠️ 注意："配置单点"是**设计意图**，并非 100% 严格——`vision/hand_pose.py` 第 70 行还自带一份 `FINGER_ORDER` 副本（见[第 10 节注意事项 10.11](#1011-finger_order-在-visionhand_posepy-有一份重复副本)）。

## 3. 模块 docstring（第 1–17 行）：设计依据与关节 ID 约定

```python
# -*- coding: utf-8 -*-
"""
hand_config.py —— RY-H1(16) 灵巧手配置（Windows 版）
依据《RY-H1(16)灵巧手用户使用手册》+ 官方 demo（知识库）：
  * 关节角度 ID 1~16（控制接口用"关节 ID"）
  * 每指 3 电机（电机 ID = 关节内电机编号）
  * 换算系数与左右手规则（demo update_motor_positions）
...
"""
```

逐条解释 docstring 中的三句"依据"：

| 依据声明 | 含义 | 出处 |
|---|---|---|
| 关节角度 ID 1~16（控制接口用"关节 ID"） | 上层（视觉/GUI/换算层）统一用**关节 ID** 作为坐标，1~16 与下面的列表一一对应 | 手册"关节定义"章节 |
| 每指 3 电机（电机 ID = 关节内电机编号） | 拇指/食指/中指/无名指/小指各由 3 个电机驱动，电机 ID 与关节 ID 重合（1~15）；第 16 关节单独对应 16 号电机 | 手册"电机分布"章节 |
| 换算系数与左右手规则（demo update_motor_positions） | 角度→电机指令的公式 `M1=k(θ1/2+θ2)`、`M2=k(−θ1/2+θ2)`、`M3=k3·θ3`、`M16=k16·θ16` 以及左手时 M1↔M2 交换，全部照抄官方 demo 的 `update_motor_positions` | 官方 demo 源码 |

docstring 中给出的**关节 ID 完整清单**（也是全局最权威的一份注释，GUI 与换算层都以此为准）：

| 关节 ID | 名称 | 关节 ID | 名称 |
|---|---|---|---|
| 1 | 拇指侧摆 | 9 | 中指远节 |
| 2 | 拇指近节 | 10 | 无名指侧摆 |
| 3 | 拇指远节 | 11 | 无名指近节 |
| 4 | 食指侧摆 | 12 | 无名指远节 |
| 5 | 食指近节 | 13 | 小指侧摆 |
| 6 | 食指远节 | 14 | 小指近节 |
| 7 | 中指侧摆 | 15 | 小指远节 |
| 8 | 中指近节 | 16 | 第16关节（0~110°） |

规律：**每指 3 个关节 = [侧摆, 近节, 远节]，按 拇指→食指→中指→无名指→小指 的顺序连续编号**。第 16 关节是独立的"拇指内外展"（水平面旋转）关节，不参与"每指 3 关节"的规律——这是它需要单独一套范围（0~110°）和单独换算系数（K16）的根本原因。

## 4. 手指 → 电机映射（第 19–29 行）

```python
FINGER_MOTOR_IDS = {
    "thumb":   [1, 2, 3],
    "index":   [4, 5, 6],
    "middle":  [7, 8, 9],
    "ring":    [10, 11, 12],
    "pinky":   [13, 14, 15],
}
MOTOR_NUM = 16
JOINT_NUM = 16
FINGER_ORDER = ["thumb", "index", "middle", "ring", "pinky"]
```

### 4.1 `FINGER_MOTOR_IDS` —— 手指 → 电机 ID 映射字典

- **含义**：每个手指名（英文字符串键）→ 该手指 3 个电机的 ID 列表，顺序 `[电机1, 电机2, 电机3]`。
- **来源**：手册"电机 ID = 关节 ID"的约定（电机 1 对应关节 1，依此类推），因此列表内容与第 3 节关节 ID 清单完全一致。
- **取值范围**：键固定为 `thumb/index/middle/ring/pinky` 五键；值为 `[1,2,3]` 到 `[13,14,15]` 的连续三元组。
- **被谁使用**：目前**主要是文档性/结构描述用途**——换算层 `angles2motor.py` 并未直接查这个字典（它用 `FINGER_ORDER` + `finger_idx*3` 的算术定位），GUI 与控制器也没有运行时读取它。它存在的意义是把"电机 ID 与手指的对应关系"固化下来，供人阅读、测试脚本与未来扩展使用。
- **为什么这样设定**：把"物理结构"（每指 3 电机）显式建模为数据，避免在代码里散布 `thumb=[1,2,3]` 之类的硬编码；任何手指与电机的对应关系改动只需改这里。
- **⚠️ 特别提醒**：该字典**只覆盖电机 1~15**，**不含 16 号电机**。第 16 关节（拇指内外展）由单独常量 `JOINT_NUM`/`K16`/`ANGLE_RANGE_DEG["joint16"]` 处理——这是设计使然，不是漏写（详见注意事项 10.4）。

### 4.2 `MOTOR_NUM = 16` / `JOINT_NUM = 16`

- **含义**：电机总数 = 16，关节总数 = 16。
- **来源**：硬件规格（RY-H1(16) 即"16 自由度/16 电机"）。
- **为什么设两个名字**：语义不同——`MOTOR_NUM` 表示执行器（电机）数量，`JOINT_NUM` 表示控制坐标（关节角度）数量。在 RY-H1(16) 上两者数值相等（关节与电机一一对应），但概念上一个是"硬件侧"，一个是"软件坐标侧"。换算层 `angles2motor.py` 校验"必须恰好 16 个角度"、控制器 `hand_controller.py` 校验 `len(angles_rad_16) != JOINT_NUM` 都依赖它。
- **被谁使用**：`JOINT_NUM` 被 `hand_controller.py`（`move_joints` 入参校验）与 GUI（`gui/main_gui.py`、`gui/hand_gui.py`、`apps/mimic_demo.py` 中初始化 16 长度的状态数组/滑块）广泛引用；`MOTOR_NUM` 主要作为包级导出供外部了解硬件规模。
- **修改影响**：理论上若未来换 20 关节的手，改这一个数 + 各表即可——但注意 16 还硬编码在别处（`hand_controller._init_bus` 的 32 个 AddListen 循环、`parse_servo_data` 的位域解析等），所以它不是唯一开关（见注意事项 10.13）。

### 4.3 `FINGER_ORDER = ["thumb", "index", "middle", "ring", "pinky"]`

- **含义**：手指遍历顺序，与关节 ID 编号顺序一致（拇指 1-3 → 食指 4-6 → 中指 7-9 → 无名指 10-12 → 小指 13-15）。
- **被谁使用**：`angles2motor.py` 的 `angles_to_motor_cmds` / `motor_cmds_to_joint_angles` 用它遍历 5 根手指（`for finger_idx, finger in enumerate(FINGER_ORDER)`），通过 `base = finger_idx * 3` 定位每指的 3 个关节下标。**顺序一旦改变，换算结果就会错乱**——它是"角度数组下标 ↔ 手指"的唯一权威映射。
- **为什么这样设定**：与手册关节编号顺序严格一致，保证 `angles[0:3]=拇指`、`angles[3:6]=食指`…这一切片约定对全系统成立。
- **⚠️ 重复定义警告**：`vision/hand_pose.py` 第 70 行存在一份**内容相同但独立**的 `FINGER_ORDER`（视觉侧用于手指遍历），两处必须保持一致（详见注意事项 10.11）。

## 5. 关节角度范围 `ANGLE_RANGE_DEG`（第 31–37 行）

```python
# 关节角度范围（度，伸直=0°）
ANGLE_RANGE_DEG = {
    "swing":   (-20.0, 20.0),
    "prox":    (  0.0, 90.0),
    "dist":    (  0.0, 75.0),
    "joint16": (  0.0, 110.0),
}
```

### 5.1 逐键详解

| 键 | 含义 | 范围（度） | 对应关节 | 来源 | 被谁使用 |
|---|---|---|---|---|---|
| `swing` | 侧摆关节 | `(-20.0, 20.0)`（左右对称 ±20°） | 每指第 1 个关节（ID 1,4,7,10,13） | 手册"侧摆 ±20°" | `angles2motor._clamp_angle_rad` |
| `prox` | 近节（掌指）关节 | `(0.0, 90.0)` | 每指第 2 个关节（ID 2,5,8,11,14） | 手册"近节 0~90°" | `angles2motor._clamp_angle_rad` |
| `dist` | 远节（指间）关节 | `(0.0, 75.0)` | 每指第 3 个关节（ID 3,6,9,12,15） | 手册"远节 0~75°" | `angles2motor._clamp_angle_rad` |
| `joint16` | 第16关节（拇指内外展） | `(0.0, 110.0)` | ID 16 | 手册"第16关节 0~110°" | `angles2motor._clamp_angle_rad` |

### 5.2 三条关键约定

1. **单位是"度"**：虽然系统内部（视觉 → 换算层接口）统一用**弧度**，但这个字典的值是**度**。`angles2motor.py` 在钳位前先把弧度转成度（`_clamp_angle_rad` 内部用 `math.radians(lo_deg/hi_deg)` 换算回弧度再比较），所以这里写度更接近手册原文、更易审查。
2. **"伸直 = 0°"**：所有关节的 0° 定义是"手指完全伸直"。因此伸直时 16 个角度全为 0 → 电机指令全为 0（**不是** 2048 中点），`open_hand()` 就是下发 16 个 0。
3. **侧摆是唯一双向（含负值）关节**：`swing` 是唯一允许负角度的关节（`-20~+20`），对应左右两侧摆；其余关节都是单向弯曲（0 起）。

### 5.3 为什么范围上限 90/75/110 恰好是换算系数 K12/K3/K16 的分母

这不是巧合：**`ANGLE_RANGE_DEG` 的机械行程上限，就是换算系数把"满行程 → 满量程 4095"的归一化基准**（见第 7 节推导）。两者必须同步修改，否则会出现"角度被钳位了但换算系数还按旧行程算"的不一致。

## 6. 中文关节名 `JOINT_NAMES_CN`（第 39–47 行）

```python
JOINT_NAMES_CN = [
    "拇指侧摆", "拇指MCP", "拇指PIP",
    "食指侧摆", "食指MCP", "食指PIP",
    "中指侧摆", "中指MCP", "中指PIP",
    "无名指侧摆", "无名指MCP", "无名指PIP",
    "小指侧摆", "小指MCP", "小指PIP",
    "拇指内外展"
]
```

- **含义**：长度为 16 的列表，`JOINT_NAMES_CN[i]` = 关节 ID `i+1` 的中文显示名。
- **被谁使用**：**纯显示用途**——`gui/main_gui.py`（滑块标签 `f"{i+1}:{JOINT_NAMES_CN[i]}"`）、`gui/hand_gui.py`（`f"{i:2d} {JOINT_NAMES_CN[i]}"`）、`apps/diag_motor.py` 的诊断输出。不参与任何数值计算。
- **命名细节与解剖学近似**：
  - 拇指用"侧摆/MCP/PIP"，四指用"侧摆/MCP/PIP"；其中 **MCP（掌指关节）≈ 近节、PIP（近端指间关节）≈ 远节**，与 `ANGLE_RANGE_DEG` 的 `prox`/`dist` 一一对应（`prox`→MCP、`dist`→PIP）。
  - 第 16 关节显示为 **"拇指内外展"**（水平面内拇指绕掌心的开合旋转），与 docstring 中的"第16关节"互为补充描述。
- **为什么这样设定**：GUI 滑块数量多（16 个），中文短名 + 关节 ID 前缀让操作者一眼定位；MCP/PIP 是机械手领域的通用解剖学命名，比"近节/远节"更专业，但注意它们**不是**严格医学定义（真实的 PIP 是"近端指间关节"，这里借用作"远节"的代称）。

## 7. 换算系数与位置满量程（第 49–52 行）：4095 的来源与 K12/K3/K16 推导

```python
K12 = 4095.0 / 90.0
K3 = 4095.0 / 75.0
K16 = 4095.0 / 110.0
POS_MAX = 4095
```

### 7.1 `POS_MAX = 4095` —— 12 位 PWM 位置分辨率满量程

- **4095 是怎么来的**：灵巧手每个电机的 PWM 位置控制是 **12 位分辨率**，位置指令取值范围 `0 ~ 2^12 − 1 = 0 ~ 4095`。`4095 = 2^12 − 1`，即 12 个 bit 全 1。
- **含义**：`POS_MAX` 是"位置指令满量程"，也是所有换算系数的分子。位置指令 0 = 行程一端，4095 = 行程另一端（具体哪端对应伸直/弯曲，由机械安装决定；系统约定 0°=伸直 对应 0 指令）。
- **佐证**：`hand_controller.py` 的 `parse_servo_data`/`parse_servo_info` 用 `& 0xFFF`（12 位掩码）从回执帧中解出位置——硬件协议层就是 12 位位置字段。
- **被谁使用**：`angles2motor._clamp` 的默认上限（`hi=POS_MAX`）；`hand_controller.move_motor` 的位置钳位（`max(0, min(POS_MAX, ...))`）；`move_joints` 换算后的指令本身就在 0~4095。

### 7.2 `K12 = 4095.0 / 90.0 ≈ 45.5` —— 侧摆 + 近节的联合系数

这是全文件**最重要的一个系数**，对应官方 demo `update_motor_positions` 的核心公式：

```
k = 4095 / 90
M1 = k·(θ1/2 + θ2)      θ1 = 侧摆角（度），θ2 = 近节角（度）
M2 = k·(−θ1/2 + θ2)
```

**分母 90 为什么是 90，而不是侧摆的 20？** —— 因为每指前两个关节（侧摆 + 近节）由**两个电机（电机1、电机2）联合驱动**，类似"差速驱动"结构：

- **共模分量**（两电机指令之和）负责**近节弯曲**：

  ```
  (M1 + M2) / 2 = k·[(θ1/2 + θ2) + (−θ1/2 + θ2)] / 2 = k·θ2
  ```

  近节行程 `0~90°` 被 `k = 4095/90` 线性映射到满量程 `0~4095`。**这就是分母 90 的来源：近节行程 90°**。

- **差模分量**（两电机指令之差）负责**侧摆**：

  ```
  M1 − M2 = k·[(θ1/2 + θ2) − (−θ1/2 + θ2)] = k·θ1
  ```

  侧摆角 θ1 以"两电机指令之差"的形式叠加；因为差动天然"一人一半"，所以公式里写的是 **θ1/2**——侧摆 ±20° 只产生 `±20°·k/2 = ±455` 的差值（相对共模偏置）。

**为什么这样设计**：近节弯曲是"大行程、大负载"的主运动（0~90°，需要两电机合力），侧摆是"小行程、小负载"的辅运动（±20°），用同一对电机以"共模带弯曲、差模带侧摆"的方式复用一个机械自由度对，是灵巧手紧凑化设计的典型结构。换算系数必须按**主行程（近节 90°）**归一化，才能保证近节满行程恰好等于满量程。

### 7.3 `K3 = 4095.0 / 75.0 = 54.6` —— 远节系数

```
M3 = K3·θ3 = (4095/75)·θ3
```

- 远节关节由**单个电机（电机3）**直接驱动，行程 `0~75°`（`ANGLE_RANGE_DEG["dist"]`），所以系数 = 满量程 4095 ÷ 行程 75°。
- 含义：远节每弯 1° ≈ 54.6 个位置单位。

### 7.4 `K16 = 4095.0 / 110.0 ≈ 37.23` —— 第16关节系数

```
M16 = K16·θ16 = (4095/110)·θ16
```

- 第 16 关节（拇指内外展）由**16 号电机**独立驱动，行程 `0~110°`（`ANGLE_RANGE_DEG["joint16"]`），系数 = 4095 ÷ 110。
- 含义：该关节每转 1° ≈ 37.23 个位置单位——比其它关节"单位角度对应的位置码更少"，所以**同样的角度差，第 16 关节的视觉位移看起来更小**（这也是控制器里专门提供 `check_joint16_stroke` 排查"16 号电机幅度小"的背景之一）。

### 7.5 正/逆换算公式汇总（含推导）

**正向：关节角度 → 电机指令**（`angles2motor.angles_to_motor_cmds`，与 demo 完全一致）：

| 电机 | 公式 | 行程依据 |
|---|---|---|
| M1 | `K12·(θ1/2 + θ2)` | 近节 90° + 侧摆差动 |
| M2 | `K12·(−θ1/2 + θ2)` | 同上（差模取反） |
| M3 | `K3·θ3` | 远节 75° |
| M16 | `K16·θ16` | 第16关节 110° |
| （左手 hand_lr=0） | 每指 `M1 ↔ M2` 交换 | 左右手镜像安装 |

**逆向：电机指令 → 关节角度**（`angles2motor.motor_cmds_to_joint_angles`，由正向公式反解）：

```
θ1 = (M1 − M2) / K12          # 侧摆（差模）
θ2 = (M1 + M2) / (2·K12)      # 近节（共模）
θ3 = M3 / K3
θ16 = M16 / K16
```

**为什么要写成 `4095.0 / 90.0` 而不是 `45.5`**：① 保持"满量程/行程"的物理含义可读；② 用浮点字面量 `4095.0` 避免 Python 3 中整数除法 `4095/90` 仍返回浮点的歧义（此处明确标注浮点更稳妥）；③ 未来行程变更时只需改分母，与 `ANGLE_RANGE_DEG` 联动。

### 7.6 极限组合与钳位（数学边界）

设 `k = 4095/90`：

- 近节 90° + 侧摆 +20°（同向最大）：`M1 = k·(10 + 90) = 45.5 × 100 = 4550 > 4095` → 被 `_clamp` 钳到 **4095**（`M2 = 45.5×80 = 3640`，正常）。
- 近节 0° + 侧摆 +20°：`M1 = 455`，`M2 = −455 < 0` → 被 `_clamp` 钳到 **0**。

这说明**"近节满弯曲 + 侧摆满摆"或"近节伸直 + 侧摆"在数学上会超出单电机 0~4095 的量程**，`_clamp` 正是为此兜底。实际使用中侧摆通常配合一定的近节弯曲才表现完整；若发现"伸直状态下侧摆幅度小"，这是换算几何的固有边界（结合电机行程配置一起排查，见控制器 `check_all_strokes`）。这是**设计边界而非 bug**，但值得在使用层知晓（详见注意事项 10.5）。

```python
HAND_CONFIG = {

    "k12": K12, "k3": K3, "k16": K16,
    "angle_range_deg": ANGLE_RANGE_DEG,
    "default_speed": 1000,
    "default_max_current": 75,
    "cmd_pos_vel_cur": 0xAA,
    "cmd_pos_vel":     0xA1,
    "cmd_get_status":  0xA0,

    "listen_num": 33,
    "update_rate_ms": 20,
    "timeout_ms": 10,
}
```

**字典的总体作用**：把散落在本文件的全部配置聚合成一个可整体传递/序列化/打印的字典。目前实际消费方是 `hand_controller.py`（读 `default_speed`、`default_max_current`、`hook_num`、`listen_num`）；其余键是"协议/参数档位"的权威登记，供上层按需读取或作为文档化配置。**注意**：`k12/k3/k16`、`angle_range_deg`、`position_max` 是前面顶层常量的"副本引用"（同一个对象），换算层直接 import 顶层常量而不是查字典——两条路径值永远一致。

### 8.1 `position_max`（= 4095）

- **含义**：电机位置指令最大值，即 12 位满量程（见 7.1）。
- **来源**：硬件分辨率（2^12 − 1）。
- **作用**：字典内自描述；外部若按字典驱动（如序列化配置到 UI），用此键即可获得钳位上限，不必 import `POS_MAX`。

### 8.2 `k12` / `k3` / `k16`（= 45.5 / 54.6 / 37.23）

- **含义**：三个换算系数的字典副本。
- **来源**：与顶层 `K12/K3/K16` 同一对象。
- **作用**：把"换算系数"与"行程/分辨率"放在同一个配置字典里，便于整体传递；换算层仍直接 import 顶层常量（见第 9 节）。

### 8.3 `angle_range_deg`（= `ANGLE_RANGE_DEG`）

- **含义**：四类关节角度范围的字典副本。
- **作用**：同上，聚合进字典；换算层直接 import 顶层 `ANGLE_RANGE_DEG`。

### 8.4 `default_speed = 1000`

- **含义**：运动**速度默认值**，作为 `RYH1HandController(default_speed=...)` 的构造默认值，进而作为 `move_joints` / `move_motor` 未显式指定速度时的速度参数，最终传入 SDK `RyMotion_ServoMove_Mix` / `RyMotion_ServoMove_Speed` 的速度字段（`c_uint16`）。
- **来源**：官方 demo 常用的典型速度值。
- **取值范围**：SDK 速度参数为 16 位无符号（0~65535），与位置指令 0~4095 同量纲的"位置单位/秒"（或厂商定义的速度档位，具体单位以手册为准）。1000 ≈ 满量程 4095 的 1/4，是"跟手且平稳"的经验折中。
- **在运动控制中的作用**：`move_joints` 逐电机下发 0xAA/0xA1 指令时，若调用方没传 speed，就用它。改大 → 动作更快但更冲；改小 → 更慢更稳。
- **为什么这样设定**：视觉模仿需要"实时跟手"（速度不能太低）又需要"不抖不撞"（不能全速），demo 的 1000 是厂商验证过的平衡点。

### 8.5 `default_max_current = 75`

- **含义**：**最大电流保护默认值**，即每个运动指令里的电流上限参数（`c_uint16`），传入 SDK 运动函数。
- **来源**：官方 demo 常用值。
- **单位/取值**：厂商电流单位（常见为 mA 或 0.1A 档，以手册为准），demo 取 75。
- **作用**：电机堵转/过载时电流达到该上限即限制输出，是防止烧电机、防止撞到机械限位时硬顶的软保护。`move_joints`/`move_motor` 未显式指定时使用。
- **为什么这样设定**：配合灵巧手小电机额定电流，75 是 demo 验证过的"够力又不伤机"的值；如需更强抓握力可调大，但会提高过流风险。

### 8.6 `cmd_pos_vel_cur = 0xAA` —— 位置+速度+电流（力位混合）指令码

- **含义**：CAN 数据帧**载荷第 1 字节**（命令字节）为 `0xAA`，表示"位置 + 速度 + 电流"三参数运动指令——即**力位混合模式**。
- **来源**：厂商协议（手册"运动指令"章节；官方 demo 中 `0xAA` 即三合一运动帧）。
- **在运动控制中的作用**：
  1. **下发**：`hand_controller.move_joints` / `move_motor` 在 `control_mode=0` 时调用 `RyMotion_ServoMove_Mix`，SDK 内部构造的命令帧首字节即 0xAA，携带 (motor_id, position, speed, current)；
  2. **回执监听**：`_init_bus` 中为 16 个电机各注册一个监听 `0xAA` 的 `AddListen`（ID = 电机ID+256），用于**接收运动完成/位置回执帧**，经 `_listen_cb` 解析进 `_last_servo_info`。
- **为什么需要三合一**：视觉模仿时希望"同时约束位置、速度、电流"，既快速到位又限制力矩，避免抓取时过度施力。`0xAA` 是默认模式（`control_mode=0`）。

### 8.7 `cmd_pos_vel = 0xA1` —— 位置+速度（两参数）指令码

- **含义**：命令字节 `0xA1` 表示"位置 + 速度"两参数模式（**不含电流控制**）。
- **作用**：`hand_controller` 在 `control_mode != 0` 时调用 `RyMotion_ServoMove_Speed`，SDK 底层发出 0xA1 帧。用于不需要电流约束的场合（如纯位置测试）。
- **为什么与 0xAA 分开**：协议层面两套指令格式不同（载荷长度/字段不同）；配置字典把它们登记为命名常量，上层用 `control_mode` 选择，避免散落魔法数字。注意 `lib/PCAN_ruiyan16.py`（旧版直连库）里也硬编码了 0xAA 命令字节，与新 SDK 路径并存（见注意事项 10.10）。

### 8.8 `cmd_get_status = 0xA0` —— 状态查询指令码

- **含义**：命令字节 `0xA0` 表示"查询电机状态"（位置/速度/电流/故障码等，回执 8 字节）。
- **作用**：
  1. **轮询读取**：`get_servo_info` → SDK `RyFunc_GetServoInfo` 底层发 0xA0 查询帧并等回执；
  2. **异步监听**：`_init_bus` 为 16 个电机各注册一个监听 0xA0 的 `AddListen`，把状态回执持续灌入 `_last_servo_info`，支撑 `check_connection` 连接性自检与 GUI 状态面板。
- **为什么需要**：连接性自检（`check_connection` 靠"有应答的电机数 > 0"判断链路通）、故障码监控（status≠0 → 过温/过流/堵转/找零告警等，见 `SERVO_STATUS_TEXT`）都依赖 0xA0 查询。

### 8.9 `hook_num = 40` —— SDK 总线"消息钩子"槽位数

- **含义**：`RyCanServoBusT.usHookNum` 字段的值，即 SDK 内部**消息钩子（MsgHook）缓冲容量**。钩子是 SDK 用于消息分发/回调注册的内部机制（每个监听、每个待处理消息都会占用钩子）。
- **来源**：官方 demo 总线初始化用的 `hook=40`。
- **在总线初始化中的作用**（`hand_controller._init_bus`）：
  ```python
  HookArr = MsgHookT * HAND_CONFIG["hook_num"]   # 40 个钩子
  self.bus.usHookNum = HAND_CONFIG["hook_num"]   # 写进总线结构体
  ```
  在调用 `RyCanServoBusInit` 之前必须把该字段与 `pstuHook` 指向的数组准备好；SDK 初始化时据此建立内部消息表。
- **为什么是 40**：需要覆盖 32 个 AddListen 各自关联的钩子 + SDK 内部收发消息占用的钩子 + 余量。40 是 demo 验证过的安全容量；**过小会导致初始化失败或回调丢失**，过大只是多占一点内存（每个 MsgHookT 几十字节，可忽略）。

### 8.10 `listen_num = 33` —— 监听表容量

- **含义**：`RyCanServoBusT.usListenNum` 字段的值，即**监听器（MsgListen）表容量**。监听器 = "对某个 CAN ID + 命令字节的组合注册一个接收回调"。
- **来源**：官方 demo 用的 `listen=33`。
- **在总线初始化中的作用**（`_init_bus`）：
  ```python
  ListenArr = MsgListenT * HAND_CONFIG["listen_num"]   # 33 个监听槽
  self.bus.usListenNum = HAND_CONFIG["listen_num"]
  # 随后注册 32 个 AddListen：16×0xA0（状态）+ 16×0xAA（位置回执）
  ```
- **为什么是 33 而不是 32**：实际注册 32 个监听（16 电机 × 2 命令），33 留 **1 个余量**，给 SDK 内部临时监听或未来扩展（如新增 0xBE 回零回执监听）用。32 个监听的结构：前 16 个监听 `0xA0`（状态），后 16 个监听 `0xAA`（运动回执），CAN ID 均为 `电机ID + 256`。
- **为什么不能小于 32**：`AddListen` 会把监听写入该表，容量不足会越界/失败，导致状态与回执收不到——`check_connection` 表现为"有应答电机数为 0"。

### 8.11 `update_rate_ms = 20`

- **含义**：**状态更新周期**（毫秒）——对应 SDK `RyParam_SetUpateRate` 的更新率参数；20ms = 50Hz 状态上报/更新节拍。
- **来源**：官方 demo 的参数档位。
- **作用（当前实现状态）**：`hand_controller._declare_api` 已声明 `RyParam_SetUpateRate` 的 ctypes 签名（`bus, motor_id, rate, fdb, timeout`），但**当前代码尚未用该常量显式调用它**——即这是一个"预留给更新率 API 的权威默认值"，与 demo 对齐登记在配置单点。若未来需要调节电机状态回执频率（如降低总线负载或提高监控刷新率），在此修改即可。
- **为什么 20ms**：50Hz 与视觉控制主循环节拍（约 20ms/帧）匹配；过快会挤占 CAN 总线带宽（1Mbps 下 16 电机 × 多命令帧），过慢则 GUI 状态刷新与跟手延迟明显。

### 8.12 `timeout_ms = 10`

- **含义**：**通用同步调用超时默认值**（毫秒），对齐 demo 的轮询/等待粒度。
- **作用（当前实现状态）**：与 `update_rate_ms` 类似，目前**没有代码路径直接读取 `HAND_CONFIG["timeout_ms"]`**——各 API 调用点在调用时显式传入自己的超时（如 `get_servo_info(timeout_ms=100)`、`get_stroke(100)`、`homing(1000)`、运动函数最后参数传 0 表示等待回执）。它登记的是"系统级默认等待节拍"的参考值。
- **为什么 10ms**：SDK 内部对命令回执的等待/重试通常以 10ms 为粒度轮询（`_rx_loop` 也是 1ms 步进刷新 tick 计数）；10ms 是"一帧往返"量级的合理默认。

## 10. 常见误解与注意事项

### 10.1 4095 是"位置码"，不是"角度单位"

`POS_MAX=4095` 是 12 位 PWM 的位置码满量程（`2^12−1`），与角度是**两套坐标系**：角度（度/弧度）是物理坐标，位置码（0~4095）是电机指令坐标，两者通过 K 系数互转。不要试图用 4095 去理解角度。

### 10.2 K12 的分母 90 是"近节行程"，不是"侧摆范围"

侧摆 ±20° 不直接进分母——它靠 M1/M2 **差模**实现且幅值减半（θ1/2）。分母 90 的唯一依据是近节 0~90° 满行程要映射到满量程。若误把 K12 分母改成 20，近节换算会放大 4.5 倍，动作直接越界。

### 10.3 "伸直=0°"意味着 0 指令是伸直，不是中点

系统约定伸直时所有角度为 0 → 电机指令 0（PWM 行程一端），**不是 2048**。因此 `open_hand()` 下发的是一串 0。若有人按"伺服中点=2048"的思路初始化，整个手会处于错误姿态。

### 10.4 `FINGER_MOTOR_IDS` 只含 1~15，不含 16 号电机

字典覆盖拇指到小指共 15 个电机；16 号电机（第 16 关节/拇指内外展）由 `K16`、`ANGLE_RANGE_DEG["joint16"]`、`JOINT_NAMES_CN[15]` 单独处理。这是设计使然（它不属于任何"手指的 3 电机组"），不是遗漏。

### 10.5 极限角度组合会触发钳位（数学边界）

- 近节 90° + 侧摆 ±20°：M1 可达 4550 > 4095 → 被 `_clamp` 截到 4095；
- 近节 0° + 侧摆：其中一个电机指令为负 → 被钳到 0，侧摆表现受限。
这是差速结构的固有几何边界。若实测"伸直时侧摆幅度小"，先确认换算几何（本文件）再排查行程配置（`RyParam_GetStroke`，见控制器 `check_all_strokes`）。

### 10.6 指令码 0xAA/0xA1/0xA0 是"数据载荷第 1 字节"，不是 CAN ID

这三个值是 CAN 帧**数据域**的命令字节；伺服帧的 **CAN ID = 电机 ID + 256**（`_init_bus` 中 `ulId = i + 1 + 256`，接收端 `mid = msg.ulId & 0xFF`）。用总线抓包排查时别把命令字节当 ID 过滤。

### 10.7 左右手（hand_lr）不改映射表，而是换算后交换 M1↔M2

`hand_lr=1` 右手 / `0` 左手，实现位置在 `angles2motor` 的换算**之后**（`cmds[base], cmds[base+1] = cmds[base+1], cmds[base]`）。因为左右手电机 1/2 安装方向镜像，共模（近节）/差模（侧摆）的物理含义互换。**症状判断**：如果"拖近节滑条，实际动的是侧摆"，通常是手型选反了——调 `set_hand_lr` 即可，无需重连。

### 10.8 `hook_num=40` / `listen_num=33` 必须 ≥ 实际使用量

实际注册 32 个 AddListen（16×0xA0 + 16×0xAA）。`listen_num` 不能小于 32，否则初始化失败或监听越界，表现为"电机无应答/状态收不到"；33 留 1 个余量。`hook_num=40` 覆盖 32 监听 + SDK 内部消息。这两个值是"缓冲容量"，改小有风险，改大无收益（仅少量内存）。

### 10.9 `update_rate_ms` / `timeout_ms` / `cmd_*` 目前是"登记的默认值"，改了不会自动生效

当前运行代码：`RyParam_SetUpateRate` 只声明未调用；`timeout_ms` 无读取点；指令码在 `_init_bus` 中是硬编码的 0xA0/0xAA。**修改这些键不会改变现有行为**——它们是对齐 demo 的权威登记（配置单点的文档化职责）。若要真正生效，需在调用点接入（如给 `get_servo_info` 的默认超时改读 `HAND_CONFIG["timeout_ms"]`）。**不要误以为"改配置=改行为"**。

### 10.10 新旧两套命令路径并存

`hand/hand_controller.py` 走官方 RyCAN SDK（`RyhandLibx64.dll`），`lib/PCAN_ruiyan16.py` 是旧版直连 CAN 库（也硬编码 0xAA 命令字节）。两者协议指令一致但实现独立，改协议时需同步两边，避免"配置与直连库行为不一致"。

### 10.11 `FINGER_ORDER` 在 `vision/hand_pose.py` 有一份重复副本

`vision/hand_pose.py` 第 70 行自带 `FINGER_ORDER = ["thumb", "index", "middle", "ring", "pinky"]`（视觉侧遍历手指用）。内容必须与本文件一致——否则视觉侧的角度排列顺序与电机侧换算顺序错位，会出现"动食指，实际动中指"类的张冠李戴。改一处记得同步另一处。

### 10.12 修改本文件常量后需要重启进程

这些是**模块级常量**，import 时求值，无热加载机制。运行中改文件不会生效；且 `HAND_CONFIG` 中部分是**对象引用**（如 `angle_range_deg` 直接指向 `ANGLE_RANGE_DEG`），运行时改字典会同时影响换算层，易造成状态不一致——**统一在文件里改、重启生效**最安全。

### 10.13 16 这个数字并不只存在于本文件

虽然 `JOINT_NUM/MOTOR_NUM = 16` 是权威定义，但"16"还硬编码在：`hand_controller._init_bus` 的 32 个 AddListen 循环（`range(16)`×2）、回执解析的 12 位位域、`move_joints` 的逐电机循环等。换更大关节数的手时，这些都要同步改——本文件不是唯一的开关。

### 10.14 侧摆的 0° 是"正中"，弯曲类关节 0° 是"伸直"

`swing` 范围 `(-20, 20)` 对称，0° = 侧摆正中；`prox/dist/joint16` 范围从 0 起，0° = 完全伸直。GUI 滑条与日志显示时注意：侧摆滑块的中值（0）对应机械正中，而弯曲滑块的最小值对应伸直。

### 10.15 MCP/PIP 是近似命名

`JOINT_NAMES_CN` 中 MCP ≈ 近节（prox）、PIP ≈ 远节（dist），是机械手行业的通用叫法，并非严格解剖学术语（真实 PIP 是"近端指间关节"）。阅读手册时以手册的"近节/远节"为准，本文件以 `ANGLE_RANGE_DEG` 的 `prox/dist` 为数值权威。

## 11. 术语速查表

| 术语 | 含义 |
|---|---|
| 关节 ID | 1~16 的控制坐标编号（1-3 拇指、4-6 食指、7-9 中指、10-12 无名指、13-15 小指、16 第16关节） |
| 电机 ID | 1~16，与关节 ID 一一对应（每指 3 电机，电机 ID = 关节 ID） |
| 侧摆 / prox / dist | 每指 3 关节：侧摆 ±20°、近节 0~90°、远节 0~75° |
| 第16关节 | 拇指内外展（水平面旋转），0~110°，16 号电机独立驱动 |
| 位置码 | 0~4095 的 12 位 PWM 位置指令（2^12−1） |
| K12/K3/K16 | 换算系数 = 4095 ÷ 对应行程（90/75/110） |
| 共模 / 差模 | M1、M2 之和表示近节弯曲，之差表示侧摆 |
| 0xAA | 位置+速度+电流（力位混合）运动指令 |
| 0xA1 | 位置+速度运动指令 |
| 0xA0 | 状态查询指令 |
| hook / listen | SDK 总线内部消息钩子缓冲 / 监听器表（40 / 33） |
| hand_lr | 1=右手、0=左手（换算后每指 M1↔M2 交换） |
